# Deploy esy free on Render

Genuinely $0, no account-verification wall. One Docker web service (the
[Dockerfile](../Dockerfile)) builds the React SPA, bundles it into the Spring
Boot jar, and serves **both** the SPA and `/api` on one HTTPS URL — so the
frontend's relative `/api` calls work with no CORS.

## Free-plan caveats

- The instance **sleeps after ~15 min idle**; the next request cold-starts (~30–60s).
- DB is **in-memory H2** (Render's free plan has no persistent disk), so data
  resets on restart/redeploy. `DataInitializer` reseeds products; dev-login
  still works every run. Fine for a demo; not for real orders.

## Deploy (one time, ~5 min of your input)

The repo is already on GitHub (`OtoGvazava/esy`) with [render.yaml](../render.yaml).

1. Sign up at **https://render.com** (GitHub login is easiest — no card for free).
2. **New + → Blueprint**.
3. Connect/select the **`OtoGvazava/esy`** repo. Render reads `render.yaml`
   and shows one service `esy` (Docker, Free).
4. **Apply** / **Create**. First build takes ~5–8 min (Node + Maven in Docker).
5. Open the service URL: `https://esy.onrender.com` (or the name Render assigns).

`JWT_SECRET` is auto-generated by Render (`generateValue: true`). Nothing else
to configure.

## Verify

- Storefront loads products (MacBook Pro / AirPods Pro — the seeded "main" tenant).
- Sign in: globe/account → email `admin@esy.shop` → Verify → shop-owner; or
  Gmail/iCloud buttons. Admin product CRUD works.
- Deep links (e.g. `/product/5`, `/cart`) load directly (SPA fallback).

## Gmail (Google OAuth) sign-in

The code is fully wired (server-side Google OAuth2 → JWT → SPA). It only needs
a Google OAuth client — **you** create this; I can't make accounts or hold the
secret. "Continue with Gmail" stays inert until these env vars are set.

1. **Google Cloud Console** (https://console.cloud.google.com) → create/select a
   project → **APIs & Services → OAuth consent screen**: External, app name
   `esy`, your support email; scopes `openid`, `email`, `profile`. While it's in
   *Testing*, add your Google account under **Test users** (or Publish the app).
2. **Credentials → Create credentials → OAuth client ID → Web application**.
   **Authorized redirect URIs** (exact, both):
   - `https://<YOUR-RENDER-HOST>/login/oauth2/code/google`
   - `http://localhost:8080/login/oauth2/code/google`  (local dev)
   (No "Authorized JavaScript origins" needed — it's a server-side flow.)
3. Copy the **Client ID** and **Client secret**.
4. **Render** → your service → **Environment** → add:
   - `GOOGLE_CLIENT_ID` = …
   - `GOOGLE_CLIENT_SECRET` = …
   Leave `APP_OAUTH2_REDIRECT_BASE` unset (same-origin). Save → it redeploys.
5. **Local dev**: run the backend with
   `GOOGLE_CLIENT_ID=… GOOGLE_CLIENT_SECRET=… APP_OAUTH2_REDIRECT_BASE=http://localhost:5173`
   plus `npm run dev` for the web. "Continue with Gmail" → Google → back signed in.

Notes: the JWT, cookie-based OAuth state (works under stateless sessions), and
`{baseUrl}` redirect resolution behind Render's TLS proxy are all handled in
code and verified. iCloud stays a dev stand-in (Apple OAuth not configured).

## Redeploy

`autoDeploy: true` — every push to `main` rebuilds and redeploys automatically.

## Persistence (required for real signup / accounts / orders)

H2 is in-memory → every redeploy/restart wipes signed-up stores, accounts,
memberships and orders. The platform (store signup, the cross-store account
hub, orders) is only "real" with a database.

**Local (one command):** `docker compose up --build` → http://lvh.me:8092
(platform) and http://&lt;sub&gt;.lvh.me:8092 (tenant stores — `*.lvh.me`
resolves to 127.0.0.1 via public DNS, no `/etc/hosts`). Runs Postgres + the
app with `JPA_DDL_AUTO=update`; data survives restarts (named volume
`esy_pgdata`; `docker compose down -v` wipes it). See CLAUDE.md
"Multi-tenant + real Google sign-in (lvh.me)" for the full clean setup.

**Render:** add a **Render PostgreSQL**, then on the web service set
`SPRING_DATASOURCE_URL` (jdbc:postgresql://…), `SPRING_DATASOURCE_USERNAME`,
`SPRING_DATASOURCE_PASSWORD`, `JPA_DDL_AUTO=update`. The backend already reads
these (`application.yml`); the postgres driver is bundled. The free Render
plan has no managed Postgres for long — this is the paid path.

Account model: one global `User` (unique email/username) + `StoreMembership`
(OWNER/CUSTOMER) + `Order`/`SavedItem`/`StoreFollow`. `GET /api/account`
aggregates it. JPA creates the tables; no manual migration.

**Product photos** are stored in the **database** (`product_images`, bytes as
Postgres `bytea` / H2 `BLOB`) and streamed from
`GET /api/products/{id}/images/{imageId}` — no object store, no Render disk.
They therefore persist exactly like everything else: durable on Postgres
(compose volume / Render PostgreSQL), wiped on every restart on the free
in-memory H2 plan. If image volume/CDN ever matters, the swap point is
`ProductImageService` (move bytes to Cloudflare R2 / S3 behind the same API).

## Wildcard subdomains + OAuth (the platform's multi-tenant path)

Tenant stores resolve by `Host` (`<sub>.esy.ge`); the platform is `esy.ge` /
`www.esy.ge`. To run real wildcard tenants with working Gmail sign-in:

1. **Render paid instance** + add the apex and a wildcard custom domain
   (`esy.ge`, `www.esy.ge`, `*.esy.ge`). Wildcard certs need a paid plan.
2. **DNS**: `A`/`ALIAS` apex + `CNAME *` → the Render host, plus the ACME
   validation record Render shows for the wildcard cert.
3. **One** Google redirect URI only — the canonical host:
   `https://www.esy.ge/login/oauth2/code/google` (Google forbids wildcard
   redirect URIs). Set `APP_OAUTH2_CANONICAL_ORIGIN=https://www.esy.ge` on the
   service. `OAuthCanonicalHostRedirectFilter` funnels every tenant's OAuth
   through that host and returns the JWT to the originating store — already
   coded + tested; it's a no-op when the env var is unset (local/dev).
4. Keep `APP_OAUTH2_REDIRECT_BASE` unset in prod (same-origin).

**Locally the same funnel runs on `lvh.me`:** set
`APP_OAUTH2_CANONICAL_ORIGIN=http://lvh.me:8092` and register
`http://lvh.me:8092/login/oauth2/code/google` in Google Console. `lvh.me` is a
real registrable domain (`*.lvh.me` → 127.0.0.1, public DNS), so the
`Domain=lvh.me` SSO cookie behaves exactly like prod's `Domain=esy.ge`. The
host allowlist (`AuthCookie` / `TenantOrigins` / `TenantContextService` /
`SecurityConfig`, plus web `storeUrl` / `isPlatformHost`) already covers it.
